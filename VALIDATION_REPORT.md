# Validación de PulseFlow

Fecha: 2026-07-22. Revisión de código sobre el estado actual del repositorio (versión 1.2.0 del csproj) más una evaluación analítica de rendimiento, ya que el sandbox de esta sesión no tiene el SDK de .NET instalado ni acceso de red a nuget.org/dot.net para instalarlo. Se dejó preparado un proyecto de BenchmarkDotNet en `benchmarks/PulseFlow.Benchmarks` para que lo corras localmente con `dotnet run -c Release --project benchmarks/PulseFlow.Benchmarks` y así tengas números reales en tu máquina.

## Veredicto general

El diseño general es sólido y sigue el patrón estándar de wrapper cacheado que usan MediatR y librerías similares (ConcurrentDictionary de Type a wrapper genérico, evitando reflection repetida en el camino caliente de comandos y queries). Sin embargo encontré un bug real de tipado, una inconsistencia entre lo que promete el README y lo que hace el csproj, y dos puntos donde el propio código no sigue el mismo cuidado de rendimiento que aplicó en el Mediator: la validación con FluentValidation y el despachador de eventos de dominio. Ninguno de estos problemas es grave para uso interno, pero si vas a publicar esto como paquete NuGet público conviene resolverlos antes, porque son justo el tipo de detalle que alguien escéptico de CQRS (como tú) señalaría al mirar el código.

## Hallazgos de diseño y bugs

En `Application/Mediator/Mediator.cs`, tanto `Send(ICommand)` como `Send<TResponse>(IQuery<TResponse>)` usan el mismo diccionario estático `SendWrappers` para cachear sus wrappers, indexado únicamente por `Type`. Hoy funciona porque en la práctica ningún tipo implementa a la vez `ICommand` e `IQuery<T>`, pero es una dependencia implícita no documentada ni protegida por el compilador: si alguna vez una clase implementara ambas interfaces (por ejemplo un tipo compartido en una migración de código), el primer `Send` que se ejecute fijaría el wrapper en el diccionario y el segundo intentaría castear al tipo equivocado, lanzando una `InvalidCastException` en tiempo de ejecución en vez de un error de compilación. Separar en dos diccionarios (`CommandWrappers` y `QueryWrappers`) cuesta nada y elimina el riesgo por completo.

El método `Send<TResponse>(IStreamQuery<TResponse> query, ...)` está declarado `async Task<IAsyncEnumerable<TResponse>>` pero su cuerpo no tiene ningún `await`; el compilador debería marcarlo con la advertencia CS1998 porque el método corre de forma síncrona a pesar del modificador `async`. Más allá de la advertencia, envolver un `IAsyncEnumerable` dentro de un `Task` obliga al consumidor a un doble await (`var stream = await mediator.Send(query); await foreach (var item in stream)`), cuando lo natural y lo que hacen MediatR y la mayoría de librerías similares es exponer directamente `IAsyncEnumerable<TResponse> Send(...)` sin el `Task` exterior. Vale la pena corregir la firma de la interfaz.

`Domain/DomainEventDispatcher.cs` resuelve y ejecuta los handlers de eventos de dominio usando `dynamic` (`Cast<dynamic>()` y `await handler.Handle((dynamic)domainEvent)`). Esto es notablemente más lento que el patrón de wrapper genérico cacheado que se implementó cuidadosamente en `Mediator.cs`, porque cada llamada con `dynamic` pasa por el DLR (Dynamic Language Runtime), que resuelve el binding en cada call site con más overhead que una invocación tipada, incluso con el cache de call-site que mantiene el propio DLR. Es la inconsistencia de rendimiento más clara del código: se resolvió bien el problema en un lugar y no en el otro, cuando la solución es la misma (un wrapper genérico como `SendCommandWrapper<T>` pero para `IDomainEventHandler<T>`).

En `Application/Validation/FluentValidationBehavior.cs`, la línea `Type.GetType("FluentValidation.IValidator\`1, FluentValidation")` se ejecuta en cada request que pasa por el pipeline, no una sola vez. `Type.GetType` con nombre calificado por ensamblado no es gratis: hace parsing del string y búsqueda en los ensamblados cargados cada vez. Lo mismo pasa con los `GetMethod("Validate", ...)` por cada validador en cada request. Nada de esto está cacheado, a diferencia del resto del Mediator donde sí se cachean los wrappers por tipo. Cachear el `Type` resuelto (o directamente un booleano "FluentValidation está presente") en un campo estático, y cachear el `MethodInfo` de `Validate` por tipo de validador, elimina prácticamente todo este costo con un cambio pequeño.

Tanto `ValidationBehavior` como `FluentValidationBehavior` serializan los errores de validación a un string JSON (`JsonSerializer.Serialize(new { errors = errorsByProperty })`) y lo guardan en la propiedad `Error` de tipo `string?` de `Result`. Esto tiene dos costos: performance (serializar JSON en cada validación fallida cuando probablemente el caller solo necesita iterar la lista de errores) y ergonomía de API (el consumidor tiene que deserializar ese string para recuperar los errores estructurados, perdiendo el tipado). Si el objetivo es que `Result` sea explícito y tipado, probablemente valga más la pena una lista de errores estructurada en el propio `Result` en vez de un string JSON oculto detrás de `Error`.

El README dice explícitamente "Dependency-Free: No external runtime dependencies, ensuring a lean footprint", y el comentario XML de `AddFluentValidationIntegration` dice "This method does not require a compile-time dependency on FluentValidation". Sin embargo, `PulseFlow.csproj` tiene `<PackageReference Include="FluentValidation" Version="12.1.1" />` como referencia directa del paquete, además de `Microsoft.Extensions.DependencyInjection` y `Microsoft.Extensions.Logging`. Es decir, cualquiera que instale PulseFlow desde NuGet se trae FluentValidation como dependencia transitiva, contradiciendo tanto el README como el propio comentario del código, que sugiere que la integración es puramente reflexiva y opcional. O se quita la referencia directa a FluentValidation del csproj (dejando que la resolución por reflection funcione solo si el consumidor la instaló aparte, que es lo que el código realmente hace) o se corrige la documentación para dejar de llamarse "dependency-free".

`AddMediator()` sin argumentos escanea `AppDomain.CurrentDomain.GetAssemblies()`, que solo contiene los ensamblados ya cargados en memoria en el momento exacto de la llamada. Si el ensamblado que contiene tus handlers todavía no fue cargado por el runtime en ese punto (por ejemplo si se carga de forma diferida), `AddMediator()` simplemente no lo va a encontrar y vas a tener errores de resolución de DI en tiempo de ejecución sin ningún aviso en tiempo de compilación. Es el mismo gotcha que tenían versiones antiguas de MediatR y ya lo documentas parcialmente, pero vale la pena ser aún más explícito en el README y quizás lanzar una excepción descriptiva cuando `AddMediator()` no encuentra ningún handler, en vez de fallar silenciosamente hasta el primer `Send`.

Finalmente, no encontré ningún proyecto de tests en el repositorio. Para una librería que ya está en NuGet y que depende de reflection y generics en varios puntos críticos (los wrappers del Mediator, el descubrimiento de handlers y validadores, el cast de `Result<T>` dentro de `ValidationBehavior`), tener aunque sea una suite básica de tests unitarios cambia mucho la confianza para refactorizar sin romper nada, especialmente antes de tocar los puntos anteriores.

## Rendimiento: qué esperar y cómo validarlo tú mismo

Con el diseño actual, el camino caliente de un `Send` sin behaviors hace: un lookup en `ConcurrentDictionary` (rápido, ya cacheado), dos resoluciones de `IServiceProvider` (el handler y la lista de behaviors), y la construcción de un `Func<Task<Result>>` por request. Eso es comparable en orden de magnitud al overhead de MediatR clásico (basado en DI, no en source generators): del orden de un puñado de microsegundos por request en un entorno .NET moderno, dominado más por la resolución de DI que por el patrón en sí. Frente a cualquier operación real de I/O (una consulta a base de datos, una llamada HTTP), ese overhead es ruido.

Los dos puntos que si vale la pena medir con cuidado son el `dynamic` de `DomainEventDispatcher` y el `Type.GetType`/reflection sin cache de `FluentValidationBehavior`, porque ahí sí hay trabajo repetido evitable en cada llamada, a diferencia del resto del Mediator que ya está bien cacheado. El proyecto de benchmark que dejé en `benchmarks/PulseFlow.Benchmarks` compara llamada directa al handler vs `Mediator.Send` sin behaviors vs `Mediator.Send` con tres behaviors (Exception, Performance, Validation) para que veas la magnitud real en tu hardware; con `[MemoryDiagnoser]` activado también vas a ver cuántas allocations agrega cada capa, que suele ser más revelador que el tiempo en sí para este tipo de decisión.

## Prioridad sugerida

Si tuviera que ordenar por impacto relativo al esfuerzo: primero resolver la contradicción de dependencias en el csproj/README porque afecta la confianza de cualquiera que instale el paquete; segundo separar los diccionarios de wrappers de comandos y queries porque es un cambio trivial que cierra un bug latente; tercero cachear la resolución de tipos en `FluentValidationBehavior` y reemplazar el `dynamic` de `DomainEventDispatcher` por un wrapper tipado, ya que es donde realmente se pierde rendimiento evitable; y por último, si el tiempo lo permite, una suite mínima de tests antes de la próxima versión.
