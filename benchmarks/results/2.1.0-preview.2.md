# PulseFlow 2.1.0-preview.2

Run on 2026-09-26 after the per-container dispatch plans (one dictionary lookup per call, pipeline facts cached in
the wrapper, outermost behavior invoked without an extra delegate). Same machine as previous runs: AMD Ryzen 5 3600,
Windows 11, .NET 10.0.11 (desktop, not an isolated benchmark machine).

Compared with [2.1.0-preview.1](2.1.0-preview.1.md):

| Scenario | preview.1 | preview.2 | Change |
|---|---|---|---|
| Send | 52.4 ns · 56 B | 38.9 ns · 56 B | -26% |
| Send (singleton) | 49.9 ns · 32 B | 36.6 ns · 32 B | -27% |
| Send + 2 behaviors | 180.2 ns · 488 B | 120.3 ns · 384 B | -33%, -104 B |
| Send + 2 behaviors (singleton) | 173.1 ns · 376 B | 88.2 ns · 272 B | -49%, -104 B |
| Publish to 2 handlers | 60.2 ns · 88 B | 65.3 ns · 88 B | see note (76 ns in the full run, fixed) |
| Stream 10 items | 217.3 ns · 208 B | 199.6 ns · 208 B | -8% |

Note on Publish: the full run below measured 76 ns, a real regression confirmed by a focused re-run (74 ns). It was
not the wrapper cache (moving it back to a static cache still gave 80 ns) but a `try/catch` added to the publish
method for the single-handler shortcut: a method with exception handling is compiled less efficiently by the JIT
even when that path is not taken. Moving the `try/catch` to its own method brought Publish back to **65.3 ns**
(Mediator 14.0 ns, MediatR 325.6 ns: 4.99x faster than MediatR, 11.45x less memory).
